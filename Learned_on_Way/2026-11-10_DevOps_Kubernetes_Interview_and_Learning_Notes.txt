PART B — KUBERNETES ARCHITECTURE CONCEPTS
Deployment → ReplicaSet → Pods
• Deployment YAML includes replicas, selector, Pod template, container image, ports and resources.
• A Deployment typically creates/manages ReplicaSets; the ReplicaSet controller maintains desired Pod count.
• Changing replicas from 3 to 5 creates two additional Pods without necessarily creating a new ReplicaSet.
• Scheduler chooses a suitable worker node for an unscheduled Pod; kubelet and container runtime start its containers.
• If a Pod is deleted, ReplicaSet creates a replacement. If only a container crashes within an existing Pod, kubelet may restart that container.


HPA — Horizontal Pod Autoscaler
• Changes number of Pods, e.g., 3 → 5, using CPU/memory or other supported metrics.
• Usually configured in hpa.yaml; minReplicas, maxReplicas and target metrics.
• CPU utilization targets are relative to CPU requests, not CPU limits.
• HPA controller is built into Kubernetes; CPU/memory scaling requires a working resource metrics pipeline.


VPA — Vertical Pod Autoscaler
• Recommends or changes container CPU/memory requests, e.g., 250m/256Mi → 500m/512Mi.
• Usually configured in vpa.yaml with targetRef, updatePolicy and resourcePolicy.
• VPA components (recommender, updater, admission controller) generally need separate installation.
• Depending on mode and cluster capabilities, applying changes may recreate Pods or update resources in place. VPA does not simply add Pods.
• HPA and VPA may conflict if both control CPU/memory-related dimensions of the same workload; plan their combination carefully.


How resource metrics reach HPA
Linux kernel/cgroups measure usage → kubelet exposes resource statistics → Metrics Server periodically scrapes kubelets over HTTPS → Kubernetes metrics API → HPA controller reads metrics → updates Deployment scale.
• Metrics Server typically runs as a separate Pod in kube-system on a worker node; it can collect from all nodes.
• Metrics Server is not installed inside each application Pod.
• Common checks: kubectl top nodes; kubectl top pods; kubectl get hpa; kubectl describe hpa <name>.
• If Metrics API is unavailable, CPU/memory-based HPA cannot make normal decisions from those missing metrics.
• VPA uses observed resource usage and recommendations over time, not a simple fixed CPU threshold.


Worker nodes, Pods and containers
• In EKS with EC2 nodes: EKS cluster → worker node (EC2) → Pods → containers.
• One worker node hosts multiple Pods; one Pod can contain multiple containers.
• Containers within one Pod share a network namespace and Pod IP; they can communicate via localhost and distinct ports.
• Kubernetes schedules Pods, not independent containers inside a Pod.


Kubernetes Pod networking
• CNI = Container Network Interface; the standard for network plugin integration.
• Amazon VPC CNI is commonly supplied with EKS and configures Pod networking and VPC-subnet IP assignment.
• The aws-node DaemonSet normally runs one networking agent Pod per eligible worker node.
• CNI sets up connectivity; it is not necessarily a packet-by-packet intermediary.
• Pods on different worker nodes can communicate directly by Pod IP when routing and security rules permit; a Kubernetes Service is not required for direct IP traffic.
• A Service gives stable DNS/virtual IP access to changing backend Pods. kube-proxy or an alternative data plane implements Service forwarding.
• CoreDNS resolves Kubernetes Service names.
• Example checks: kubectl get daemonset aws-node -n kube-system; kubectl get pods -n kube-system -l k8s-app=aws-node -o wide.

PART E — EKS CONTROL-PLANE UPGRADE INTERVIEW SCENARIO (ADDED 10 NOVEMBER 2026)
Interview question: How would you upgrade the Kubernetes control plane in Amazon EKS?
Answer framework:
1. Assess the current and target versions, supported one-minor-version-at-a-time upgrade path, cluster health, deprecated Kubernetes APIs, workload compatibility, add-on versions, webhooks and tooling.
2. Test the process in a non-production cluster, plan a maintenance window, communicate risks and prepare recovery procedures. EKS control-plane Kubernetes version upgrades cannot be downgraded.
3. Initiate the EKS control-plane upgrade via console, CLI or infrastructure as code. Example (replace the target version with a supported one): aws eks update-cluster-version --name my-cluster --kubernetes-version <target-version> --region ap-south-1
4. Confirm the upgrade completed and the API server is reachable; upgrade compatible managed add-ons such as VPC CNI, CoreDNS and kube-proxy according to AWS guidance.
5. Upgrade managed node groups or self-managed EC2 workers through controlled rolling replacement, respecting PodDisruptionBudgets, readiness probes, replica availability and workload capacity.
6. Validate application health, DNS, Pod networking, metrics, logs, CI/CD and autoscaling; monitor closely after the upgrade.
Follow-up interview question: The EKS control plane has been upgraded from 1.32 to 1.33, but EC2 worker nodes remain on 1.32. Will applications immediately stop?
Answer: No. Control plane and kubelet versions can temporarily differ within the supported Kubernetes/EKS version-skew rules. Existing workloads do not automatically fail just because the control plane moves ahead one minor version. Schedule compatible worker-node upgrades next; do not leave version skew unmanaged.
Important nuance: The exact allowed version skew depends on Kubernetes version and EKS policy; it is not universally limited to exactly one minor version. Verify the applicable supported policy for the cluster.
Short revision Q21: Who manages the EKS control plane? A: AWS.
Short revision Q22: Can you downgrade an upgraded EKS Kubernetes control plane? A: No.
Short revision Q23: Should worker nodes be upgraded before or after the control plane? A: Normally after the control plane, within the supported version-skew policy.
Short revision Q24: Does a 1.33 control plane necessarily break 1.32 worker nodes? A: No; compatible versions can coexist temporarily.
Short revision Q25: What protects workloads during rolling node upgrades? A: Sufficient replicas and capacity, readiness probes, PodDisruptionBudgets and monitoring.
